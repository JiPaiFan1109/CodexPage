# 3.5.0 图片预览缓存预算

开发版本仍为 3.5.0，未安装、打包或发布，未操作真实壁纸库或生产 Codex。本轮保留已有视觉、预览解码尺寸与此前所有未发布优化。

## 已确认的问题与实现

缩略图（通常 640 像素宽）和专注预览（1600 像素宽）共用一个最多 64 项的 LRU 缓存。64 项只是数量限制，不是内存限制。隔离测试中，17 张 1600×900 的 PNG 就能留下 97,920,000 字节的估算像素量，约 93.38 MiB。

在 `scripts/skin-manager.ps1` 中保留 64 项上限与最近使用顺序，并增加 64 MiB 估算像素预算。按实际解码宽高、至少 32 位的像素格式和 4 字节行对齐估算；高于 32 位的格式按自身位深计算。初始化时计数归零，插入/淘汰时增减计数，命中时仅调整最近使用顺序。单张超预算图片仍解码并返回显示，但不进入缓存，也不清空其他图片。

相同测试下，最终留下 11 项、63,360,000 字节（约 60.42 MiB），较原样本少 34,560,000 字节（约 32.96 MiB）。最近查看的图片仍复用；被淘汰的较旧图片回看时需要重新解码。这是空间与回看速度的取舍，64 MiB 是本轮选定的预算，并非已证明对所有设备最优。

该预算**不是进程 RAM 或显存上限**。解码器临时内存、WPF/GPU 资源、控件正在引用的图片及其他应用状态不在预算内；移出缓存也不保证立即回收。没有缩小图片分辨率，没有证明整个进程内存减少上述数值。

## 开源与依赖

先核对 [dotnet/wpf 开源项目](https://github.com/dotnet/wpf)（MIT）。沿用项目已经使用的 WPF，不迁移框架、不安装依赖、不复制第三方代码。估算依据 WPF 原生 [BitmapSource.Format](https://learn.microsoft.com/en-us/dotnet/api/system.windows.media.imaging.bitmapsource.format?view=windowsdesktop-9.0) 与 [PixelFormat.BitsPerPixel](https://learn.microsoft.com/en-us/dotnet/api/system.windows.media.pixelformat.bitsperpixel?view=windowsdesktop-9.0)；为低位深图片预留至少 32 位表面的空间是本项目策略。

## 性能成本与迭代

初版每次插入遍历所有缓存项计数，交替测量 64 张缩略图首次读取时，各轮多用约 118、237、129 ms，因此未保留此实现。最终改为增量记账。初版日志与计时保存在 `.local-evidence/performance-memory-20261106/initial-scan/`。

最终计时脚本先预热一轮，再交替三轮读取 64 张 640 像素宽图片。原版/新版首次读取时间（ms）分别为 871.93/507.75、396.58/525.40、435.85/391.12；缓存命中分别为 140.08/71.29、53.50/70.23、66.17/64.22。波动较大，结果没有稳定方向，不声称此改动提高速度；它避免了初版每次插入遍历整份缓存的固定工作。代价仍包括估算和记账，以及大图被更早淘汰后的再次解码。

## 验证与证据

证据目录 `.local-evidence/performance-memory-20261106/`；本轮前源码快照 `before/skin-manager.ps1`，原版红测试 `red.log`，最终脚本结果 `checks.json`，交替计时 `timings.json`。新测试原版按预期失败于超过 64 MiB；新测试覆盖预算、实时总量一致性、热图复用、旧图淘汰、超大图显示但不驻留、文件句柄释放、48 位像素行对齐及低位深保守估算。

既有缓存测试继续检查 64 项边界、文件变化/损坏/删除、图标、实时路径保护和解码宽度隔离。回归还覆盖损坏图片句柄、预览、专注预览及实际隔离 WPF 媒体流程。`integration.png` 是隔离 WPF 捕获，不是生产截图。最终通过范围和源码哈希由 `final-verification.json` 记录。没有测试全部 GPU、物理多屏 DPI、长时间进程内存峰值；本轮不能作为内存泄漏已全面排除的证明。

最终 6 个相关 Windows 脚本、57 项 Node 测试、184 个 PowerShell 解析通过；只读独立复核无阻塞。已检查隔离截图，图库缩略图、选中边框与主要控件正常显示，无本轮新增视觉改动。源码哈希核对保留此前图库、运行时与切换优化。
